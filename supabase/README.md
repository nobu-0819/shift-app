# 肉匠のログインと他店社員権限

ログイン画面はスタッフコードとパスワードを使う。コードは内部の Supabase Auth 識別子に変換する。メールアドレスの入力やメール送信は不要。スタッフの既存IDを Auth アカウントに結び付け、希望シフトの関連を維持する。

- 管理者は管理ページの変更操作とアカウント管理を行える。
- 他店社員は管理ページの既存情報を閲覧し、希望一覧を印刷できる。シフト提出の対象者には含めない。
- 一般スタッフは自身の希望・未提出設定だけを変更できる。
- 仮パスワードで入った直後は、アプリのデータにアクセスする前に本人がパスワードを変更する。再発行前のセッションも無効になる。

## テスト環境と切り替え

1. 本番のスキーマと権限を取得し、個人を特定できる情報を取り除いたコピーで検証する。特に、既存のポリシー、公開ビューや関数、関連テーブルの外部キー、同じ Supabase を参照する公開版を確認する。本マイグレーションは既存アプリのテーブルに対する匿名アクセスを廃止するので、旧画面と同時には運用できない。
2. テスト用 Supabase でマイグレーションを適用し、`nikusho-accounts` Edge Function をデプロイする。Edge Function のサービスロール鍵は Supabase の環境変数でのみ利用する。クライアントではテスト用のURLと公開鍵を使用し、Auth の公開サインアップを無効にする。
3. 最初の管理者は Authentication → Users で確認済みのアカウントを作る。内部のアドレスは下のコマンドで既存のスタッフコードから生成する。十分に長い仮パスワードを設定する。

   ```sh
   node --input-type=module -e 'import {createHash} from "node:crypto"; console.log(createHash("sha256").update(process.argv[1].trim()).digest("hex")+"@login.shift-app.invalid")' '001'
   ```

   SQL Editor で当該の既存管理者だけをリンクする。IDとAuth UIDは実値で置き換える。仮パスワードで最初にログインすると新しいパスワードの設定へ進む。

   ```sql
   update public.staff
   set auth_user_id = '<Auth の User UID>', password_setup_required = true
   where id::text = '<既存スタッフ ID>' and is_admin and auth_user_id is null;
   ```

4. 管理者がスタッフ一覧の「仮パスワードを発行」から既存スタッフを順次リンクする。コードはデータベースの既存値を使う。新規の他店社員はスタッフ一覧から登録し、「他店社員にする」を選択してから本人にコードと仮パスワードを渡す。
5. 管理者の操作、一般スタッフ本人の提出、他店社員の閲覧・印刷、他店社員の書き込み拒否、再発行後の旧セッション無効化、既存の希望・スタッフIDの維持を確認する。権限変更やEdge Function実行には本番データを使わない。
6. 本番で切り替える前に、DBのバックアップ、既存ポリシーと公開権限、現行のデプロイを控える。本番用の仮パスワードを渡す手順と復旧方法を確認してから、画面・Edge Function・DB権限を揃えて切り替える。本番へのデプロイだけでDB権限は更新されない。

パスワード発行中に障害が起きたアカウントは、過去のセッションを受け付けないようロックが残ることがある。DB管理者が Auth アカウントと staff の関連付けを点検してから復旧する。
