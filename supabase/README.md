# 肉匠のログインと他店社員権限

初回と再設定はスタッフコードを入力し、本人が新しいパスワードを決める。翌回からは同じコードとパスワードでログインする。メールアドレスと仮パスワードの配布は不要。既存のスタッフIDを Supabase Auth アカウントにリンクし、希望シフトとの関連を維持する。

- 管理者は管理ページの変更とアカウント管理を行える。
- 他店社員は管理ページの情報を閲覧し、希望一覧を印刷できる。スタッフコードは表示されず、シフト提出の対象には含まれない。
- 一般スタッフは自身の希望と未提出設定を変更できる。

登録時または管理者が「パスワード設定を受け付ける」を押した時点から、コードでの設定を15分間だけ受け付ける。管理者も他店社員も同じ操作で設定する。受付を開くと旧セッションのアクセスが止まり、設定が成功すると受付は閉じる。コードを知る人は受付中に先に設定できるため、本人がすぐ設定できるときだけ開き、コードは個別に渡す。受付の試行回数には全体の制限がある。

## テスト環境と切り替え

1. 本番のスキーマと権限を取得し、個人情報を除いたコピーで検証する。既存のポリシー、公開ビューと関数、関連テーブルの外部キー、スタッフコードの一意性、同じ Supabase を参照する公開版も確認する。匿名で既存テーブルにアクセスする旧画面とは、切り替え後は同時に運用できない。
2. テスト用 Supabase でマイグレーションを適用し、`nikusho-accounts` Edge Function をデプロイする。初回設定は未ログインで呼ぶので、`supabase functions deploy nikusho-accounts --no-verify-jwt` を使用する。関数内で、初回設定以外は Supabase が検証したセッションと権限を確認する。サービスロール鍵は Edge Function の環境変数でのみ使う。クライアントはテスト用のURLと公開鍵を使用し、Auth の公開サインアップを無効にする。
3. 最初の管理者はまだアプリに入れないため、SQL Editor で受付を開く。対象のスタッフコードを確認して、一致する既存管理者だけに実行する。対象者は15分以内に「初回・再設定はこちら」から自分のパスワードを設定する。

   ```sql
   select public.nikusho_open_password_setup(id::text)
   from public.staff
   where code::text = '<既存管理者のスタッフコード>' and is_admin;
   ```

4. 管理者が、既存スタッフには「パスワード設定を受け付ける」を押し、新規登録には登録フォームの権限欄を使う。本人が画面を開いてすぐ設定できるタイミングで受付を開始する。
5. 管理者の操作、一般スタッフ本人の提出、他店社員の閲覧・印刷と書き込み拒否、受付期限切れ・一度使用したコードでの再設定拒否、既存の希望・スタッフIDの維持を確認する。本番データを使用してテストしない。
6. 本番で切り替える前にDBのバックアップ、既存ポリシーと公開権限、現行のデプロイを控える。最初の管理者が設定できる時間を調整し、画面・Edge Function・DB権限を揃えて切り替える。

Auth 更新中に障害が起きたアカウントはロックが残ることがある。DB管理者が Auth アカウントと staff の関連付けを確認してから復旧する。
