# 肉匠のログインと他店社員権限

初回はスタッフコードを入力し、本人が数字4桁のパスワードを設定する。次回からは同じコードとパスワードでログインする。メールアドレスや仮パスワードは不要。最初の管理者も同じ方法で設定する。

- 管理者は管理ページの変更とアカウント管理を行える。
- 他店社員は管理ページの情報を閲覧し、希望一覧を印刷できる。スタッフコードは表示されず、シフト提出の対象には含まれない。
- 一般スタッフは自身の希望と未提出設定を変更できる。

新規登録時は全員が一般スタッフになる。管理者は登録後にスタッフ一覧の「管理者にする」または「他店社員にする」で権限を付与する。

初回設定に時間制限はない。既に設定済みのアカウントは、管理者が「パスワードをリセット」を押すまでコードだけでの再設定を受け付けない。リセットすると旧セッションは無効になる。未設定のコードを他人が知っていると先に設定できるため、コードは本人に個別に渡し、すぐ設定してもらう。

## テスト環境と切り替え

1. 本番のスキーマと権限を取得し、個人情報を除いたコピーで検証する。既存のポリシー、公開ビューと関数、関連テーブルの外部キー、スタッフコードの一意性、同じ Supabase を参照する公開版も確認する。匿名で既存テーブルにアクセスする旧画面とは、切り替え後は同時に運用できない。
2. テスト用 Supabase でマイグレーションを適用する。Supabase の Edge Function Secrets に環境ごとの `NIKUSHO_PIN_SECRET` として32文字以上のランダムな値を設定する。この値から Supabase Auth 用の内部パスワードを導出するため、値の変更・紛失は全員の再設定が必要になる。ソースやブラウザに公開しない。
3. `supabase functions deploy nikusho-accounts --no-verify-jwt` で Edge Function をデプロイする。ログインと初回設定は未ログインで呼ぶ。管理操作は関数内で Supabase が検証したセッションと権限を確認する。サービスロール鍵も Edge Function の環境変数でのみ使う。クライアントはテスト用のURLと公開鍵を使用し、Auth の公開サインアップを無効にする。
4. 最初の管理者は、既に管理者権限が付いているスタッフコードで「初回・再設定はこちら」から設定する。続いて一般スタッフと他店社員の設定、ログイン、閲覧・印刷、書き込み制限、使用済みコードでの再設定拒否、既存の希望とスタッフIDの維持を確認する。
5. 本番で切り替える前にDBのバックアップ、既存ポリシーと公開権限、現行のデプロイを控える。スタッフが初回設定できる時間を調整し、画面・Edge Function・DB権限を揃えて切り替える。

Auth 更新中に障害が起きたアカウントはロックが残ることがある。DB管理者が Auth アカウントと staff の関連付けを確認してから復旧する。
